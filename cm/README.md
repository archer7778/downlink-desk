# Configuration management records

**Status:** DRAFT. Not yet reviewed or approved by the configuration manager.

These records put Downlink Desk under configuration management in the manner of
[ECSS-M-ST-40C Rev.1](https://ecss.nl/standard/ecss-m-st-40c-rev-1-configuration-and-information-management/),
*Configuration and information management*. Downlink Desk is a hobby console, not a space
product, so this is a demonstration of the method at small scale, not a claim of compliance.

plan, raises and decides change requests, and audits and corrects these records. Where a record
needs a judgement rather than a fact, the field is left blank for him and marked **[CM]**.

## How a change moves

1. Raise a change request: a GitHub issue from the **Change request** form (label
   `change-request`). The issue number is the CR number: issue #12 is `CR-012`.
2. The configuration manager classifies it (class 1 or 2, as defined in the CM plan) and approves
   or rejects it in the issue.
3. Implement on a branch. Every commit message cites the CR: `CR-012: pin requirements`.
4. Merge, then run `python3 tools/cm_status.py --issues` and commit the updated `CSAR.md` and
   `metrics.csv`.
5. When the configuration manager approves a baseline, tag it: `git tag -a BL-<name> -m "..."`.
   The script reads `BL-*` tags as the record of approved configuration.

## Facts found while drafting

These came up while the records were being drafted. They're facts, not decisions; whether each
becomes a change request is the configuration manager's call.

- No baseline exists: no `BL-*` tag, and all 40 commits on `main` predate any change control.
- No workflow runs the tests. `.github/workflows/demo.yml` builds the demo only.
- `tests/test_pipeline.py::test_model_spaceweather_summary_stream` depends on the real date: it
  checks the satellite's shadow is 25–40 minutes at three times relative to now, and the mock
  orbit has short-shadow and no-shadow seasons. It passes on 2026-10-12 and fails on 2026-11-04
  (because of the sample five days earlier, 14 minutes). Details in `SCF.md`, section 12.
- `requirements.txt` sets minimum versions only, so two installs on different days can get
  different dependency versions.
- The branch `lattice-bridge` (5 commits, last 2026-10-28) is unmerged and has no change request.
- On 2026-11-04 the history of `main` was rewritten to remove links from commit messages. Trees
  were unchanged but every commit ID changed, so installed copies can no longer fast-forward and
  `deploy/update.sh` reports "held". No impact assessment was made before the change.
